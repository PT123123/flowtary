# Native indexing validation gate

No native volume collection has passed this gate yet. Do not run the test on the affected physical laptop. HypervisorPresent on a physical machine does not provide isolation.

1. Use a disposable Windows VM with an actual restorable hypervisor snapshot. Keep the test volume and OS disk in that snapshot. Record the hypervisor, snapshot identifier, guest OS build, storage type, installed minifilters (`fltmc filters`), binary hash and source fingerprint. A clean VM tests functionality; reproducing the relevant container/wcifs environment is also needed to assess the original trigger.
2. Attach a dedicated non-system NTFS virtual test disk, labelled `FLOWTARY_TEST`. Populate only this disk with staged fixtures (10k, 100k, 1m, then larger if earlier stages pass), nested directories, Unicode names, long names, executable versions, hardlinks and reparse points. Do not point scripts at the host drive or a shared host folder. Build fixtures before recording the idle baseline.
3. Create `isolated-test.json` in the guest with schema 1, the guest `COMPUTERNAME`, real `rollback_snapshot` reference, canonical `volume_guid` (`\\?\Volume{...}\`), its non-C `drive` letter and `volume_label: FLOWTARY_TEST`. Find the volume GUID with `mountvol` in the guest. Never copy a host volume GUID into the manifest.
4. In an elevated guest terminal, collect a 30-second metrics-only baseline. Run name-only collection with `--watch-seconds 60`; retain stdout report and `--metrics` JSONL. Observe another idle baseline after exit. Do not infer a plateau from only the final sample.
5. Repeat with `--resume --watch-seconds 120`. During the watch window, create/delete/rename fixtures, move a directory containing executables in/out of the workshop-shaped root, and add/remove hardlinks. Test the literal C:\workshop product boundary through offline tests; this native test deliberately excludes the guest system drive. Compare final query paths and persisted cursor to the fixture manifest.
6. Repeat after process restart and guest restart. On the disposable volume only, test journal deletion/recreation or loss of the saved cursor. Expect refusal/stale state with the previous snapshot retained, no recursive fallback and no automatic full rebuild. Do not resize or delete a journal on any host/production volume.
7. Run repeated batches and idle/recovery windows long enough to assess rates and unreclaimed growth, not only an initial build. Retain six machine dimensions, process counters, query p50/p95, absolute ranges and slopes per record/change. Resource guard numbers are preliminary abort thresholds, not acceptable leak allowances.
8. If System handles or pools grow persistently, stop the workload and preserve traces. Use guest-only WPR/ETW kernel file/filter events plus pool tags and object-type/allocation-stack evidence to distinguish application allocation, normal caching and driver leaks. A generic task-manager reading cannot identify wcifs as the leaking allocator. Restore the VM before the next experimental variant; do not continue enlarging the fixture.

The application preflight cannot verify a supplied rollback reference or enforce the hypervisor snapshot. Confirm those externally. Cancellation/timeout cannot guarantee kernel cleanup. No real-volume performance or safety claim is valid until the above artifacts have been reviewed, including a representative filter-stack configuration.
