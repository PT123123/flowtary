# Flowtary 搜索索引与系统资源方案

状态（2026-11-05）：Flowtary 快照查询协议已接入 C++ d/f 路由；查询端现能在后台加载原子发布的新快照，查询继续使用上一完整代次，发布后以短锁切换。2M 合成快照的整机六项指标和 1.66 ms 最大热查询延迟已在代次替换测试中记录。生产快照生成/USN 所有者生命周期尚未接入，C 卷兼容 provider 的真实初建仍未通过，所以真实卷索引仍未启用。只有 164 项 VHD 快照已通过早期功能闭环；不能把它当作当前 C 卷 provider 的全盘验收。六项整机指标仍是发布闸门。复现方式及限制见 `indexer/README.md` 与 `docs/INDEXER_CPP_INTEGRATION.md`。本文用于规划替代已停用的 `fd.exe` 遍历、独立建库和全盘目录监听。任何索引方案必须先通过文末的资源验收；不能以「Flowtary 进程内存很低」代替全系统成本验收。

### 2026-11-04 实测修正

新建 `FLOWTARY_TEST` VHD 上，强制 `FSCTL_ENUM_USN_DATA` + `FSCTL_GET_NTFS_FILE_RECORD` 的初建在 FRN 27 因 USA mismatch 失败；两个独立进程各请求一次，原始 1,024 字节 payload 完全相同，故不能当作一次性瞬态读数放宽校验。USN 单页 273 条记录中有 0 个重复 FRN，而该页含一个已知双硬链接文件；USN 名称记录自身不足以证明硬链接完整。`FindFirstFileNameW` 对 129 个显式文件路径返回预期名称，累计 33.879 ms，但只覆盖小型 fixture，未证明全卷调用扇出、路径到 FRN 解析或长期系统成本。

因此 USN+逐 FRN FILE_RECORD fallback 是**已实测失败的候选**，已从当前采集路径移除；FILE_RECORD 仅保留显式诊断入口。当前 `collect` 在 `QUERY_FILE_LAYOUT` 首次返回 error 50 时转到 `FSCTL_ENUM_USN_DATA` 名称/父 FRN 图，并用串行 `FindFirstFileNameW` 补全硬链接；一个 128 MiB VHD 已完成 checkpoint、恢复、USN 更新和查询的 278 项闭环。另有仅限授权 VHD 的 opt-in 目录批次 provider，通过 `FileIdBothDirectoryInfo` 按目录读取名称和 FileId，减少逐文件调用；它能校验目录 FRN、跳过 reparse 目录并在批次边界恢复，但 10,000 项 VHD 测试仍未完成。默认 provider 还没有大卷调用扇出和系统成本数据；真实 C 卷没有全量扫描。生产全卷 provider 和自动启用仍未实现。

## 目标与衡量口径

Flowtary 要同时满足三项产品要求：搜索结果毫秒级可见、支持大部分本机磁盘的文件/路径索引，以及启动后能先给出类似 Start 菜单的常用应用结果。用户指定的应用搜索规则还要求独立于 Everything：`C:\workshop` 子树中的 `.exe` 要由 Flowtary 自己索引、筛选、排序。

衡量成本时至少同时看：Flowtary 的私有字节与工作集、整机 CPU 与磁盘 I/O、System 进程句柄数、分页池与非分页池、系统提交量、索引冷启动时间和暖查询 p50/p95。映射文件页不等于零成本；它们仍使用系统物理内存和缓存。不能只拿 `flowtary.exe` 的私有内存与 Everything 比较。

## 事故背景与已确认事实

2026-10-24 的提交 `c054769` 引入自有内存/磁盘索引及 `fd.exe` 兜底，目标包括摆脱 Everything 依赖、减少 Flowtary 私有内存。其 benchmark 报告主要比较 Flowtary 与 Everything 的进程内存和搜索延迟；源码及当时记录没有 System 句柄、分页池、非分页池或 minifilter 调用栈的验收。

旧实现的搜索守护进程会在启动时按索引档位开始建库。磁盘建库对每个固定卷分别调用 `fd` 枚举目录与文件；内存层还会枚举用户目录和 `IndexDirs`。交互查询也有实时 `fd` 遍历路径，可与后台建库重叠。流式读取能限制 Flowtary 进程保存的结果缓冲，降低子进程优先级能让出部分 CPU，但都不能消除每个目录/文件触发的文件系统 I/O 与过滤驱动回调。

长扫描无输出超时按持续输出重新计时，所以它不是扫描总时长上限。查询取消登记和停止的是交互查询子进程；它不等价于取消所有后台建库。旧代码还用每盘/每根目录的 `ReadDirectoryChangesW` 监听，缓冲溢出或变更过量可能安排索引重建。

用户实测：扫描 10 秒后 System 句柄约增加 1,500；暂停 15 秒后句柄略回落且相关内核分配几乎停止增长；恢复扫描 10 秒后又增加约 1,350。System 总句柄约 950 万，非分页池约 15.9 GB，分页池提交量约 27.3 GB；Memory Compression 约 1.8 GB，不是主要占用源。若这些观察都在同一系统负载下采集，时间相关性支持扫描是触发活动，但源码不能证明 `wcifs.sys` 有缺陷，也不能证明 System 句柄数与 wcifs pool tag 是同一批泄漏对象。判定具体分配路径需要 ETW、池标签/分配栈、句柄对象类型或等价内核证据。

## 拟议架构

### 0. 一次性授权与常驻服务边界

生产路径不应让 UI 每次启动索引子进程时都调用 `runas`。安装/首次启用时由一个明确的管理员安装步骤注册 `FlowtaryIndexer` Windows 服务；以后 SCM 启动、恢复和运行服务，不再逐次弹 UAC。更换服务二进制、修改服务账户/权限、安装或卸载时仍需管理员授权。不要关闭 UAC，也不要把 UI 常驻为管理员。

提权只放在索引服务进程中。UI 通过本机命名管道发送有版本、长度上限和命令白名单的请求；服务校验调用者身份，查询与配置权限分离，拒绝任意路径、任意命令行或任意卷句柄请求。服务对每个规范化卷身份持有全局独占租约，限定同时活动卷数、批次、I/O 超时和资源守卫；退出、崩溃、服务重启都必须释放卷句柄并保留最后一份完整快照。服务启动本身不得隐式全盘扫描，初次索引只能由明确的卷配置触发。

IPC 源码审计发现：当前查询 helper 使用继承的 stdin/stdout 管道；vendored `goz-winfs::build_pipe_security` 把读写权限给所有 Authenticated Users，`pipe_server_is_trusted` 只让客户端核验服务端是否由 SYSTEM/管理员创建，并不验证连接服务端的客户端身份。该 DACL 可以用于其现有 daemon 协议，但不能原样用于具备卷权限的 Flowtary 服务。服务 IPC 必须使用安装时记录的用户 SID 定向授权，并在服务端 impersonate 后再次核对 SID；创建首实例、消息尺寸/频率限制和协议 allowlist 也要纳入测试。

已在 Win32 边界增加 `build_pipe_security_for_sid()`：只接受数字 SID 格式，为 SYSTEM/Administrators 保留完全控制，并只给指定 SID 管道读写权限、剔除创建竞争实例的权限。另新增 `pipe_client_sid_matches()`，服务端读取请求后 impersonate 客户端、比对 token 用户 SID，并在成功/失败路径恢复服务线程身份；Windows named-pipe 测试实际连接客户端验证匹配、拒绝其他 SID 和身份恢复。VolumeOwner 现在让实验性用户进程同时持有 LocalAppData 私有租约和 ProgramData 共享租约；另有服务侧共享租约入口，但当前只读查询服务还没有采集命令，因此尚未调用它。共享目录由安装器的 SYSTEM/Administrators ACL 保护。真实服务 IPC 命令协议和 writer/USN 生命周期仍未实现，因此目前不能用服务启动卷采集。

权限设计先实测能否以虚拟服务账户和最小必要特权完成卷元数据读取；只有 API/ACL 证据证明不可行时，才评估 LocalSystem，并同时限制服务必需特权、服务 SID、安装目录写权限及 IPC DACL。尚未决定或验证账户之前，不应把实验性 `collect`/`probe-volume` 命令包装成 SYSTEM 服务。服务安装器需要幂等检查版本、二进制签名/哈希与服务配置；初装或升级只在安装操作发生时请求一次 UAC，普通启动、查询、取消和状态读取不请求提升。

### 0.1 服务资源验收

安装空闲、加载快照、暖查询、单卷初建、USN 增量、取消/服务重启、空闲回落分别采集整机提交量、内存压力代理、System 句柄、磁盘活动、分页/非分页池和 CPU，并同时保留索引服务进程数据。至少做交错 baseline/workload/cooldown；报告归因限制和计数器缺失。明确验收 System 句柄与两类池的峰值/斜率、提交量净增长、查询延迟及停止后回落。服务重启不是通过泄漏验收的替代手段。

### 1. NTFS 全盘元数据索引：USN 名称初建 + USN 增量

对明确纳入索引的 NTFS 卷，优先尝试 `FSCTL_QUERY_FILE_LAYOUT` 获取名称和文件 ID；首个调用明确返回不支持时，当前 fallback 用 `FSCTL_ENUM_USN_DATA` 提供名称/父 FRN 图，再通过路径硬链接 API 补齐名称。逐 FRN `FSCTL_GET_NTFS_FILE_RECORD` 曾因稳定的 USA mismatch 在测试 VHD 失败，已不用于初建。另一个按目录批量读取名称/FileId 的 provider 仍是测试选项，尚未通过 10,000 项 VHD 完整性、重启和资源验证。所有路径只读名称和元数据，不读取文件内容；超出调用数/时间上限、路径无法解析、FileId/FRN 不匹配、USN 断档或资源守卫触发时，整代失败并保留旧快照。

初次同步先记录 USN Journal 起始位置，再枚举初始名称集合，随后回放并折叠枚举期间产生的 USN 事件，确认卷身份与 journal 连续后原子发布。常态更新只读 journal delta。journal 断档或卷身份变化时将卷标记为 stale，保留上一份可用快照，并只允许明确触发的新一代初建；不回退到 `fd`、无界 `FindFirstFile` 全树 walker 或静默重试循环。

USN/目录 API 是候选机制，不是系统安全证明。卷句柄和目录读取仍会经过存储及过滤驱动栈；测试 VHD 的小规模通过不代表长时间或大卷成本。只有在可回滚测试卷上通过完整性、重启/增量、六项整机资源斜率和停止后回落验收，才扩大数据规模。当前没有生产服务负责 snapshot writer/USN 生命周期，也没有 C 卷全量结果。

### 2. `C:\workshop` 下 `.exe` 的 Flowtary 专用索引

从同一份 NTFS MFT/USN 元数据目录构建专用 `.exe` posting/倒排表。归一化路径后，仅接收 `C:\workshop\` 边界内的后代路径并筛选 `.exe` 扩展名；盘符大小写不敏感，但 `C:\workshop-old` 不属于该根。查询路由和排名由 Flowtary 实现，不能要求 Everything 替它筛选或排序。

应用/文件查询可并行查专用 posting 与通用 NTFS 索引，再在 Flowtary 合并去重并把专用命中放在首屏优先位。专用索引必须在全盘初建期间也能先就绪；建议从 MFT 枚举流中优先抽取 workshop 相关目录/`.exe` 记录，或在已发布快照上先建 workshop posting，再继续其余卷索引。不能为 workshop 另开一条无节制递归扫描。

当前已实现的本机 fallback 仅针对 `C:\workshop`，使用有界路径枚举而非打开卷设备：最多 20,000 个 `.exe`、4,096 个目录、12 层或 1,500 ms，并跳过 reparse 目录。Flowtary 启动后台线程在 Start Menu/App Paths/AppsFolder 收集后串行预热它，路径和折叠形式缓存为不可变快照，按键查询不触发新的目录遍历。真实目录测到 63 个 `.exe`、50 个目录；启动预热约 15 ms，预热后首查询约 15 µs，热查询 p95 4.4 µs。完整六项整机曲线及限制见 `docs/APP_CATALOG_IMPLEMENTATION.md`。这是满足定制路径的窄范围能力，不代表大多数磁盘已完成全盘索引；全盘元数据索引成熟后应把这条路径并入同一快照/USN 生命周期，避免长期保留两套维护机制。

保存的 `HKCU\Software\Flowtary\IndexDirs` 当前包含 `C:\workshop` 与 `C:\software`，但不能据此把两者视为同一条产品规则。明确的专用需求是 `C:\workshop` 下 `.exe`；`C:\software` 是否成为另一条专用规则，应作为单独需求决定。

### 3. Start 菜单式快速应用目录

把快速首屏作为独立的小型 catalog：优先读取 Start Menu 快捷方式目录、已注册应用入口和已安装包的应用清单，快速生成可启动项目；用注册表变更通知和这些少数已知目录的窄范围更新维护它。结果立即可搜，不等待全盘 MFT 初建完成。

这层不是遍历 Program Files 的替代包装：禁止启动时递归扫描安装树。应用入口解析、快捷方式目标解析及文件存在性检查须有明确的数量/时间上限，避免每个候选都触发深层文件系统访问。无法解析的入口要留诊断记录，不自动扩大扫描范围。

### 4. 毫秒级查询与索引存储

在实际规模数据上比较按名称三元组/倒排 posting、路径组件索引和压缩排序记录。查询阶段只读不可变快照，取候选后做精确子串与路径规则核验，再返回有限结果；USN writer 在旁边批量更新下一代快照并原子切换。优先根/扩展名等常见条件应在候选生成时执行，避免每次全 blob 线性扫描。

内存可以高于旧 Flowtary，但必须与 System 的文件缓存、映射页和提交量一起预算。用真实数量级的卷数据记录索引大小、暖/冷查询耗时、RAM、System cache、CPU 和磁盘吞吐后，再决定常驻内存、mmap 或混合布局。不能预先把 mmap 记为零内存，也不能在没有大数据验证时保证任意子串查询一定毫秒级。

### 5. 更新和并发约束

- 每卷一个串行的枚举/更新 worker；禁止多份全盘 walker 并行。卷级句柄固定且 RAII 关闭，USN 读取/解析 buffer 有硬上限。
- 设定每批字节数、每轮 I/O 时间预算、磁盘并发上限和可暂停窗口；前台查询优先。暂停仅控制未来请求，不能视为能撤销内核已经发生的分配。
- 查询只读已发布快照，不在按键路径触发建库或同步重扫；缓存失效时明确显示对应卷不可用/更新中。
- journal overflow、解析错误、索引文件损坏都进入有界状态机：记录原因、停止该卷自动重试、保留上一份可用快照或显示 stale。绝不转入全盘目录遍历。
- 索引服务放入独立进程只为隔离用户态崩溃和限定其私有内存；它不能回收 minifilter/System 已泄漏的内核资源，不作为安全保障。

## 不采用的做法

- 不再用 `fd.exe` 作为自动建库、查询兜底或断档后的回退路径。
- 不逐文件打开/读取内容，不用全目录递归 walker 构建全盘索引，不跟随 junction、symlink 或其他 reparse point。
- 不为降低 Flowtary 任务管理器数字而把数百 MB 映射页或服务进程移到 System/其他进程名下。
- 不把线程优先级、超时、Job kill、条目上限当成内核泄漏的补救措施；它们不会撤销文件系统过滤栈已分配或遗失的对象。
- 默认不在异常内核基线的物理机试扫。用户后来明确授权本机分阶段验证、接受可能重启，因此增加了专用小型 VHD 测试和 1–4 页实际卷元数据探测；保留增长保护、记录绝对基线。不启用 Driver Verifier，不把该授权解释为无限量重试或放开资源预算。

## 发布闸门与取证计划

1. 优先在可回滚 VM 快照中建立专用 NTFS 测试卷；用户已明确授权当前物理机测试时，先用新建的独立 VHD，再进行有界实际卷读取，按数据验证决定扩大范围。先测纯元数据快照，再测 USN 持续更新，最后测 workshop 专用 posting。测试卷中保留可识别的变更用例：创建/删除/改名、重启、USN rollover、卷卸载、权限失败、reparse point 和硬链接。
2. 以固定间隔采集 System Handle Count、分页池、非分页池、系统提交量、Flowtary 私有字节/工作集、磁盘 I/O 和 CPU。同步收集 Kernel File 与 Filter Manager ETW；若仍增长，用 PoolMon 标签/内核分配栈和句柄 object type 继续归因。基线必须来自同一 VM、同一 workload 的 idle 阶段。
3. 每个阶段做短时运行—暂停—恢复对照，并按已处理记录数画资源增量；运行结束后继续观察回落/平台期。测试中只要 System 句柄或内核池出现持续正斜率、资源无法回到预先定义的基线容差，立即停止并回滚，不扩大数据量、不进入下一阶段。
4. 至少重复多轮冷启动/暖启动及 USN rollover 测试，记录 p50/p95 首屏与查询延迟、首次索引完成时间和最低/最高总内存。没有全套数据和可复核 traces 不得宣称「系统成本更低」或启用默认自动全盘索引。
5. 对无法支持安全增量索引的卷，明确标注不支持；只有经过独立资源验证后才讨论另一种 provider。fallback 永远不能是未授权的全盘 walker。

实验原型已有名称元数据采集接口、USN 增量、硬链接快照、workshop posting、常驻快照查询协议和六类整机计数器；快照查询现已进入 C++ d/f 路由。离线测试不代表真实卷通过压力测试，也不能保证零内核泄漏。小型 VHD 已通过 USN 初建/恢复/变更闭环，但大规模目录批次 provider、长时资源斜率和 C 卷 workshop 用例尚未验收；生产快照 writer、服务 USN 生命周期仍未完成。目标是通过单 worker、限批卷元数据读取和总系统成本发布门槛，去掉旧实现中随目录/文件数量扩张的无界遍历请求；系统级安全结论必须以隔离环境测量和驱动栈证据为准。短时 IPC fixture 六项指标及边界见 `docs/INDEXER_CPP_INTEGRATION.md`。
