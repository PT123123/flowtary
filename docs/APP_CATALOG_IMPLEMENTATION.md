# 快速应用目录实现状态

正式 C++ 主程序现已使用 `src/app_catalog.h`，来源限定为当前用户/公共开始菜单、HKCU/HKLM 的 32/64 位 App Paths、Shell AppsFolder。已移除原先的 Program Files 第一层目录与其可执行文件枚举，不等待全盘索引。

入口发现只收集名称和启动目标；不批量解析快捷方式目标，不探测注册项的目标文件是否存在。快捷方式执行交给 Shell 保留其参数和工作目录；读取存储目标的其他功能也不再调用可能搜索磁盘/网络的 `IShellLink::Resolve`。

默认限制为 4,096 个入口、8,192 个检查项、256 个开始菜单目录、6 层深度、1,500 ms 协作式时间预算，以及约 8 MiB 的元数据分配估算。目录和根的 reparse point 均跳过。达到限制保留部分目录并记录状态；无命中时提示列表不完整。单次 Win32/Shell 调用仍可能超过协作式预算，不能把它称为内核层硬超时。

刷新在独立工作线程执行，发现的入口一次交给 UI；刷新期间旧目录继续可搜。新结果接管前移除借用旧程序对象的行，保留正在显示的文件搜索结果。线程句柄及时关闭；后台状态独立拥有其生命周期，窗口关闭后不向旧窗口交付对象。

`src/app_catalog_watch.h` 只注册两个已知开始菜单根、少数 App Paths 键和 AppsFolder Shell 通知。变更合并等待安静窗口，重建间隔至少 5 秒；失效来源退休，不自动循环重开。没有全卷目录监听。

`src/app_icons.h` 使用一个惰性工作线程，待处理/待交付合计最多 64 个请求，UI 最多缓存 128 个应用图标。绘制只入队并先给通用图标，提取结果由 UI 接管；目录代数变化会丢弃旧请求结果。Shell 图标调用仍会产生文件系统访问，尚需实测其真实系统成本，不能仅因搬到工作线程就判为低开销。

验证：`app_catalog`、`existing_index_ui`、`existing_index_search` 通过；覆盖开始菜单 fixture、取消/数量/目录/内存估算限制、注册项合法性、通知合并与反复关闭句柄、异步图标队列和过期结果、应用目录刷新不破坏文件查询。测试只使用显式的小型 fixture 和私有注册表测试键，未扫描真实安装目录。

生产 `SearchPrograms` 函数的 1,000 条合成入口评测保留在 `logs/indexer/app-catalog-cpp-1000-20261103/`：约 5 秒发出 23,203 次查询，p50 0.1862 ms、p95 0.3699 ms、最大 2.5972 ms。Rust 指定 PID 监测器同步记录了六类整机指标及 C++ 目标进程指标。该测试没有调用真实应用发现、图标读取或 UI 绘制，不能代表完整产品的首屏时间/内存。

真实开始菜单/AppsFolder 枚举、打包应用启动、Shell 通知及图标成本尚未完成运行验收。自有 NTFS 索引到主程序的接入仍是后续任务；快速应用目录不能替代 `C:\workshop` 专用规则。
