# C++ Flowtary snapshot query integration

Status: C++ d/f dispatch and the persistent Rust snapshot query transport are connected. Production snapshot generation, live C-volume refresh, and real-volume resource acceptance remain incomplete.

## Runtime routing

- Preference `0` (automatic): use `%LOCALAPPDATA%\Flowtary\index-C.fti` when present; otherwise query Windows Search.
- Preference `1`: require the Flowtary snapshot; if absent, report unavailable without falling back to Everything or starting a scan.
- Preference `2`: query Windows Search.
- The Rust helper is `flowtary-indexer.exe` beside `flowtary.exe`. The explicit `flowtary-indexer-experimental` CMake target builds and stages it. Release/deploy copy scripts include the helper when staged.
- To include it in a normal Flowtary build, configure with `-DFLOWTARY_EXPERIMENTAL_INDEXER=ON`; the `flowtary` target then depends on the helper build. This only packages the query host and does not create a snapshot or open a volume.
- One hidden per-user child loads the snapshot once and serves newline-delimited JSON over private anonymous pipes. It starts lazily on the first Flowtary query and exits on EOF. UI input stays asynchronous on the existing latest-wins worker.
- The client refuses stale snapshots, time-truncated results, malformed replies, and requests that exceed a bounded deadline. First lazy start has a 15-second ceiling to allow the snapshot to load; each subsequent request retains a 1.5-second transport ceiling. A failed provider does not fall back to a walker. Filename terms use name postings; explicit path fragments containing `/` or `\\` route directly to the bounded path candidate query and are verified against the full path.

The application no longer contains an Everything query route. `f` and `d` use the Flowtary snapshot when selected/available, or the Windows Search catalog in automatic fallback mode. Custom Flowtary rules are evaluated by the Flowtary index.

### Corrected process sampling and five-minute query observation (2026-11-04)

Earlier harness reports that label `process_private_bytes` or `process_handles` without a target PID were measuring the benchmark sampler process, not the Flowtary query client. Do not use those earlier process figures as Flowtary process-cost evidence. The updated harness exports the Rust child PID through a test-only handoff file and samples the C++ client, Rust child, and whole machine separately. Process CPU is computed from each target's CPU-time delta and is normalized to the capacity of **all logical processors**; it is not a single-core percentage. Machine CPU remains the independent whole-machine counter.

This correction also applies to the process CPU claims in the 65-second and 100,000-query sections below: those percentages came from the sampler process and must not be presented as client/child CPU. The whole-machine measurements and IPC timings from those runs remain valid as observations of their respective windows, subject to background activity and fixture-only scope.

At ten queries per second that measured per-query CPU projects to about 0.058% of one logical processor. Windows process-time granularity and the artificial burst limit this estimate; it does not include UI painting.

During the exact query-burst sample window, all six machine metrics were captured: commit peak change −4.7 MiB; minimum available memory 8.01 GiB and pressure 74.60%–74.67%; System handle baseline 2,522,374 and peak +16; paged pool baseline 9.14 GiB / peak +0.50 MiB, nonpaged 5.27 GiB / peak +0.23 MiB; weighted whole-machine CPU 11.50%; disk busy 1.40%, read/write 0.17 MiB/s; counter errors 0. This was a 164-entry snapshot and no volume handle was opened; these deltas include background work and cannot be attributed solely to the IPC burst. The fixture measures the query IPC path only; it does not measure volume collection, real disk indexing, or a painted UI frame.

### Background snapshot-generation reload (2026-11-05)

The persistent local query host and the read-only service now watch the atomically published snapshot generation once per second. A changed generation loads on a background thread while queries continue against the last complete catalog; publication swaps the catalog under a short write lock. Each load records all six whole-machine counters and is guarded by commit, pressure, available RAM, System handles, kernel pools, disk, paging-input, and CPU limits. A failed or over-budget generation is discarded, the old complete catalog remains available, and retries back off from 5 seconds to at most 5 minutes. No full-path metadata probe is done per keystroke.

The reload smoke test atomically replaced a private copy of the 2,000,000-entry fixture and confirmed a `published` generation report while the Rust query-host PID stayed unchanged. The snapshot reload took 2.48 seconds in the background. During the same 15-second query window, 16 complete queries had p50/p95/max latency of 1.421/1.615/1.657 ms.
