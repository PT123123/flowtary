## 一、三处功能性 bug（均有实机复现）

### 1. 内存索引只扫第一个根目录

**现象**：d/f 查询时，文档/下载/程序目录下的文件搜不到（内存索引层）。

**根因**：`bf4ddfd` 编辑时误删了 `MemIndexSearch` 中关闭外层 for 循环的 `}`，
`return` 变成了循环体的一部分——每查只扫 `g_memRoots[0]`（桌面），其余根
（文档/下载/图片/程序目录/注册表 IndexDirs）全部不可达。代码能编译，
静态阅读极易漏掉。

**修复**：补回 `}`；daemon 侧「名字零命中 → 路径兜底」逻辑随之恢复正常语义。

### 2. 守护进程查询路径从未成功过

**现象**：守护进程在线时查询仍全部回落 fd/WS 慢路径；`wsquery --mem` 报
「守护进程查询失败」。

**根因**：客户端 `SearchDaemonQuery` 发词条/排除词误用 `wl`（裸词、不带换行），
而服务端按行读取（`DaemonReadLine`）——等不到行尾、5s `SO_RCVTIMEO` 超时后断连。
自 `f559492`（守护进程独立成进程）起，**该快路径一次都没成功服务过**，
所有查询都悄悄走了 fd/WS 兜底。STAT 单行所以正常——这正是排查时最重要的对照。

**修复**：改用 `wln`（带换行）。修复后同一查询 78–250ms 返回。

**教训**：客户端/服务端在同文件里各写一套收发时，协议字节级行为必须有一条
手工 socket 冒烟通道（`printf 'Q ...\n词\n' | /dev/tcp/...`）做交叉验证。

### 3. STAT 命令从未被接线

**现象**：`wsquery --memstat` 恒显示「建库中 0 条」；托盘建库状态永不更新；
`SearchDaemonStart` 每键误判守护进程离线（旧代码每次阻塞 UI 最多 3s 拉起冗余进程）。

**根因**：`DaemonStatsReply` 自守护进程诞生起就没有任何调用点——
`DaemonHandleConn` 只解析 `Q ...`，收到 `STAT` 直接 return（无应答）。

**修复**：`DaemonHandleConn` 识别 `STAT` → `DaemonStatsReply(s)`。

## 二、拼音搜索（毫秒层新功能）

d/f 文件搜索支持三种匹配语义：**原名子串 / 全拼子串 / 首字母子序列**（首字母
要求 ≥2 字符防单字母噪声）。实测：`wxcszt` → `微信测试探针文档.txt`；
`weixin` → `微信支付交易明细.pdf` 与 `Weixin.exe` 同屏（原名与拼音双路并存）；
原名中文匹配不受影响。

### 设计要点

| 决策 | 取舍 |
| :--- | :--- |
| 只在守护进程启用 | `MemPinyinStart()` 检测 exe 同目录 `dict/` 后创建 Pinyin 实例；主程序自带一份实例不重复加载；dict 缺失时 `g_py` 保持空、功能静默降级为纯名字匹配 |
| 只转含汉字的名字 | 纯 ASCII 名字跳过（`pyOffs=0` 哨兵位），拼音池仅约 30% 条目占用，内存增量几 MB |
| 存全拼而非仅首字母 | 全拼可同时支持「全拼子串」与「首字母子序列」两种查询；仅存首字母无法答 `weixin` 这类全拼查询 |
| 缓存格式 v4 | 条目行后可选 `P\t<pinyin>` 行；版本头 `FTMEMINDEX4`，旧 v3 缓存自动弃用重建一次 |
| 转换时机 | 建库/增量重建（MemListRootFd→MemPoolAdd）时转换，3.9µs/条（见下），相对 fd 遍历的分钟级成本可忽略 |
| 并发 | `g_pyMu` 串行化建库线程与维护线程的并发转换（lib 线程安全性未声明） |

### 成本实测（build\pybench 微基准，8400 条混合中文文件名）

- 单条 API：3.9µs/条（33ms/8400）
- 批量 API：0.6µs/条（5ms/8400）——**没必要为 0.3s 的全库转换引入批量重构**

### 排查插曲：不要被「根构建 113 秒」带偏

首个根（桌面 8.4 万条）建库 113s，一度怀疑拼音转换是瓶颈；微基准证明转换
总计仅 ~0.3s，大头是 **fd 在 Defender 实时防护下的文件遍历本身**（约 1ms/文件）
加上当时另一个测试守护进程在同时跑 fd 抢 I/O。调优前先用微基准归因，
再动刀。

## 三、查询延迟的真相：恒定 500ms 是冷页回填

**现象**：守护进程重启后，连续多次查询恒定 ~500ms（连 0 命中的也 500ms），
与「暖态 20–40ms」的设计目标矛盾。

**归因**（`[disks] scan ms` 日志分解）：

| 状态 | 磁盘 blob 扫描（90MB） | 内存索引扫描（35 万条） |
| :--- | :--- | :--- |
| 冷启动首查 | 218–500ms | 0ms |
| 暖态稳态 | **31–47ms** | 0–5ms（拼音匹配后） |

冷态 = mmap 页缓存回填（一次性，守护进程常驻后不再发生）；暖态达标。
**结论：系统按设计工作，不需要进一步优化**——`[mems]`/`[disks]` 两条
`FT_DF_DEBUG` 日志由此常驻（分别打印扫描毫秒与命中数）。
（2026-10-25 第二轮：冷态成本已由预热线程挪到启动期、协议开销被批量化吃掉，
见本文第七节。）

## 四、缓存落盘锁外化

**问题**：`MemIndexSaveLocked` 在 `g_memMu`（搜索锁）内序列化 + 写 41MB 缓存，
每个根增量重建完成时，进行中的查询被卡 50–150ms。

**修复**：`MemIndexSave()`——锁内仅做快照（pool 是单个 wstring，拷贝 ≈ 一次
memcpy，~5ms），序列化 + 写盘 + 原子改名全部移到锁外；新增 `g_memSaveMu`
串行化建库线程与维护线程的并发保存（两者可能同时触发）。

## 五、其余修复/优化清单

| 项 | 说明 |
| :--- | :--- |
| 孤儿 fd 治理补全 | `FdCaptureLines`（内存/磁盘索引建库路径）此前未挂 KILL_ON_JOB_CLOSE Job——杀守护进程留下继续抢磁盘 I/O 的 fd 孤儿（实测抓到 3 个）。抽 `FdWalkerJob` 进程级单例，两条 spawn 路径统一挂载；实测杀守护进程 fd 子进程随之退出 |

| 守护进程每连接一线程 | 此前串行处理连接：STAT/诊断连接排队在长查询（全 blob 扫描秒级）后面，UI 线程的建库状态轮询被 2s 收包超时整个卡住。改 `_beginthreadex` 每连接短命线程（连接间无共享可变状态），线程创建失败退回串行 |
| 客户端协议加固 | 「N <count>」头解析失败整体按失败处理（调用方正确落 fd/WS 兜底；此前把垃圾当 0 命中且 ok=true，兜底被吞）；结果行必须是 `X:\` 绝对路径（防半行垃圾进结果） |
| `SearchDaemonStart` 限频 | 拉起限频 3s 一次 + 就绪等待 3s→1s 封顶：exe 在但起不来的病态场景（端口被占/安全软件拦杀）不再逐键卡 UI |
| 磁盘命中路径归一 | blob 存 fd 风格正斜杠 + 小写盘符：命中后统一转反斜杠、盘符大写（UI 拆 title/sub、跨层去重都依赖） |
| `wsquery` 增强 | `--bench` 支持 `--mem/--disk` 走守护进程层；`--memstat` 输出「建库全部完成」判定依赖的 STAT 现已真实可用 |
| 磁盘索引查询出锁 | `GetLongPathNameW`（文件系统调用，个别路径会挂死）移出 `g_diMu`：锁内只收集小写路径，出锁后还原大小写 |

## 六、冒烟验证方法（可复用）

1. **独立端口**：`FT_DF_DAEMON_PORT=48111` 起测试守护进程——注意单实例互斥体
   `Local\Flowtary.SearchDaemon` 全局唯一，**同时只能活一个守护进程**（与端口无关），
   换端口前先杀旧的。
2. **探针文件**：在桌面/文档各放一个唯一名字的探针（如 `zz_dfprobe_a2026.txt`），
   `wsquery --mem <探针词>` 应同时命中两处——这是「内存索引只扫首根」类 bug 的
   直接判据；中文名探针 + `wx…` 首字母查询验证拼音链路。
3. **Job 治理**：`taskkill /F` 杀守护进程后 `Get-Process fd` 应为空。
4. **协议级交叉验证**：`printf 'STAT\n' | … /dev/tcp/127.0.0.1/<port>` 手工对话，
   定位客户端 vs 服务端谁在说谎。
5. 建库观测：`FT_DF_DEBUG=1` 起守护进程，`[mem]`/`[mems]`/`[disks]`/`[conn]`/
   `[qcli]` 各阶段毫秒数落 stderr。

## 七、第二轮优化：协议批量化 + 冷页预热 + mem 饱和跳过磁盘（2026-10-25 下午）

> 对照第三节基线：暖态整链 78-250ms、冷首查 218-500ms、mem 名字扫描 31-47ms。
> 本轮后实测（生产守护进程 + `wsquery --bench 8 --mem weixin`）：
> **饱和查询（200 命中）恒定 15-16ms；0 命中最坏情况（四层全扫）62-110ms。**

### 1. 查询协议批量化（整链最大头）
- 服务端响应整包一次 `send`（原 200 命中 = 200+ 次小包）；STAT 应答同样合并。
- 客户端请求一次 `send`（头 + 词条 + 排除词）；两端读取改 4KB 缓冲 `LineReader`
  （原逐字节 recv，一查上万次系统调用，客户端/服务端各一遍）。
- 两端 `TCP_NODELAY`：环回上 Nagle+延迟 ACK 对小包可叠加百毫秒级 stall。
- 协议线上兼容：逐字节读端能解析整包发送端，新旧 exe 不需成对升级。

### 2. mem 饱和跳过磁盘扫描
`DaemonHandleConn`：mem 层已拿满 maxRows 时跳过磁盘层——合并阶段磁盘条目必然
全部丢弃，语义不变。常见词（如 `weixin`）省掉 90MB blob 扫描 + 一次路径兜底。

### 3. 磁盘索引冷页预热
守护进程启动映射就绪 / 重建完成换映射后，空闲优先级线程顺序读一遍索引文件
（缓存管理器与映射视图共享同一批物理页，读文件即暖页），把首查 218-500ms 的
页缓存回填挪到用户按键之前。`FT_DF_DEBUG` 下打 `[prefetch] ms`。

### 4. mem 扫描 ASCII 快路径
`MemCaselessFind` 逐字符 `towlower` CRT 调用占名字扫描大头（165K 条 31-47ms）。
改为：词条折叠在查询入口做一次（`MemFindFolded` 收已折叠词条），haystack 侧
ASCII 内联折叠、仅非 ASCII 走 `towlower`。名字扫描降到 0-16ms。
**教训**：第一版把折叠后 `wstring` 的构造留在 per-call 里，16 万次堆分配把
快路径收益吃光——热循环里连一次分配都不能有。

### 5. 两处 bug（冒烟抓出）
- **delta 路径双反斜杠**：`DiskWatchThread` 拼路径 `root`（"C:\"）+ `L"\\"` + rel
  → `"C:\Users\..."`，UI 打开/跨层去重都会踩。改为 root 已带尾分隔符就不重复加。
- **客户端 LineReader 作用域**：头部和结果行各建一个 reader——头部 reader 析构时
  缓冲里已收到的结果行全部丢失（服务端整包 send 后，剩余数据只在对端 FIN 才醒）
  → 恒「0 命中且 ok=true」。修复：整个响应用同一个 reader。
  （手工 socket 冒烟法再次立功：raw TCP 查询正常 → 一眼定位客户端在说谎。）

### 6. wsquery
- `PrintLine` 统一补换行（原先全部输出挤成一行，grep 只能整块捞）。
- `--bench` 与 `--mem/--disk` 组合此前不可达（单查分支先 return），调整分支顺序。

### 冒烟记录
- 探针文件（桌面+文档）、手工 TCP `Q/STAT`、`wxcszt` 拼音探针全通过；
- delta 新鲜度：守护进程生命周期内新建文件 2s 内可查，路径格式正确；
- 建库期间可查（缓存先行）：daemon 起后立即查询正常返回（略旧数据）。

## 八、第三轮：展示层排序质量 + 大小写还原缓存（2026-10-25 晚）

> 实测汇总（生产守护进程）：饱和查询 15-16ms（不变）、0 命中最坏 63ms、
> **800 行大查询暖态 47-62ms**（冷 860ms 仅守护进程重启后首查一次）。

### 1. UI 排序质量：截断不应发生在排序前
- 守护层请求 200 → **800 行**：UI 的质量排序（精确8/前缀4/包含2/路径1 + 点击
  权重）只能排它看得见的行。实测 `test` 查询：前 200 池序只有 **53** 个精确/
  前缀命中，800 行里有 **393** 个——旧截断把 86% 的高质量命中挡在排序器门外。
- `scoreOf` 补**拼音档**：词在名字与路径都不存在 = 守护进程拼音命中（文本过滤
  的 WS/fd 后端不可能产出这种行）→ 与名字包含同档计分。此前拼音结果得 0 分、
  压在仅路径命中（1 分）之下，正好把拼音用户最相关的结果埋掉。
- 删掉 UI 冗余的二次路径兜底查询：守护进程内部已按层做过 name→path 兜底并
  合并，UI 再查一遍纯浪费一轮往返。

### 2. PrefetchVirtualMemory 视图预取（替换读文件预热）
顺序读索引文件只暖缓存管理器的页，映射视图首触仍付软故障 + Defender 每进程
首访问开销（实测重启后首扫 172-609ms）。改为 `PrefetchVirtualMemory` 直接对
映射视图预取（KernelBase 运行时解析，Win8.1+；地址失效时优雅失败不崩），
旧系统回落读文件。

### 3. 目录级大小写还原缓存（本轮最大）
- **归因**：磁盘层每命中一次 `GetLongPathNameW` 在本机 Defender 下 6-8ms——
  `wx` 92 条中 34 条磁盘命中 = 250ms/查；UI 提到 800 行后最坏会到秒级。
- **方案**：按目录 `FindFirstFileW` 枚举一次得整目录「小写名→真名」映射，进程
  级缓存（`shared_ptr` 值保引用稳定）；查询发现缓存缺名（新建/改名）时自愈刷新
  一次，无需监听线程同步失效。暖态零文件系统调用。
- **实测**：冷 860ms（92 条命中跨 ~50 目录的一次性枚举）→ 暖 47-62ms。
- **教训（自摆乌龙）**：第一版把「当前组件」也拼进了父目录键——查找 "users"
  时搜的是 `c:\users` 自己的子目录表（自己找自己），恒 miss → 每查询触发全量
  refresh，比 GetLongPathNameW 还慢。冒烟日志 `[case] enum` 一眼定位。

### 4. 存量 bug：delta 键形不一致（自 c054769 起）
delta 表按真实大小写反斜杠存键，blob 命中过滤却用小写正斜杠路径查——**永远
匹配不上**：已删文件一直显示、重加文件重复显示。统一为小写反斜杠键
（`g_ovAdd` 的 value 保留真实大小写路径供展示）。

### 5. wsquery
`--rows N`：指定守护进程返回行数（验证 800 行窗口与延迟用）。

### 冒烟记录
- 大小写还原正确（`Desktop`/`Program Files` 真名）；delta 新建文件 47ms 命中
  且真名显示；饱和 15-16ms / 零命中 63ms / 拼音链路回归通过；
- 新旧 exe 混跑期间未发现协议异常（本轮协议未动）。

## 九、第四轮：内存索引 delta 即时新鲜度（2026-10-25 深夜）

> 问题：内存索引的增量粒度是「整根重扫」——桌面根 113s。用户目录树里新建的
> 中文文件要等整根重建才能拼音搜索（磁盘 delta 只兜底子串层，管不到拼音）。

### 方案：把磁盘层的成熟模式搬到内存层
- **监听线程**（原样只标脏）解析事件本体：增/改名 → `GetFileAttributesW` 判型 +
  `MemNameToPinyin` 即时转拼音 → `g_memDeltaAdd`；删/旧名 → `g_memDeltaDel`。
  属性解析不持锁（个别路径挂死只拖本监听线程，与磁盘监听同铁律）。
- **MemIndexSearch**：池命中过滤 `g_memDeltaDel`（窗口快照，竞态下轮收敛）；
  尾部合并 `g_memDeltaAdd`，匹配规则与池完全一致（名字 / 全拼子串 / 首字母子序列）。
- **整根重建换入时**按根前缀折叠清表（`MemDeltaDropRoot`，Build/Maint 两处调用）
  ——重建期间的新事件由监听继续入库、下轮收敛，与磁盘索引同一容忍窗口。
- delta > 5 万条放弃增量（洪峰交给整根重建）；delta 仅驻 RAM，重启靠缓存+全量重建。

### 实测
- 新建中文探针（微信维度测试文件.txt）**2s 内 `wxcs` 首字母拼音命中**；
- 删除后 2s 内从结果消失；ASCII 新文件 31ms 命中；
- 回归：饱和 15-31ms / 零命中 63ms / 800 行暖 47-62ms 均保持；
- 根重建换入折叠路径实测正常（`[memdelta] drop root=... add=N`）。
