## 一、三处功能性 bug（均有实机复现）

### 1. 内存索引只扫第一个根目录

**现象**：d/f 查询时，文档/下载/程序目录下的文件搜不到（内存索引层）。

**根因**：`bf4ddfd` 编辑时误删了 `MemIndexSearch` 中关闭外层 for 循环的 `}`，
`return` 变成了循环体的一部分——每查只扫 `g_memRoots[0]`（桌面），其余根
（文档/下载/图片/程序目录/注册表 IndexDirs）全部不可达。代码能编译，
静态阅读极易漏掉。

**修复**：补回 `}`；daemon 侧「名字零命中 → 路径兜底」逻辑随之恢复正常语义。

### 2. 守护进程查询路径从未成功过

**现象**：守护进程在线时查询仍全部回落 fd/WS 慢路径；`wsquery --mem` 报
「守护进程查询失败」。

**根因**：客户端 `SearchDaemonQuery` 发词条/排除词误用 `wl`（裸词、不带换行），
而服务端按行读取（`DaemonReadLine`）——等不到行尾、5s `SO_RCVTIMEO` 超时后断连。
自 `f559492`（守护进程独立成进程）起，**该快路径一次都没成功服务过**，
所有查询都悄悄走了 fd/WS 兜底。STAT 单行所以正常——这正是排查时最重要的对照。

**修复**：改用 `wln`（带换行）。修复后同一查询 78–250ms 返回。

**教训**：客户端/服务端在同文件里各写一套收发时，协议字节级行为必须有一条
手工 socket 冒烟通道（`printf 'Q ...\n词\n' | /dev/tcp/...`）做交叉验证。

### 3. STAT 命令从未被接线

**现象**：`wsquery --memstat` 恒显示「建库中 0 条」；托盘建库状态永不更新；
`SearchDaemonStart` 每键误判守护进程离线（旧代码每次阻塞 UI 最多 3s 拉起冗余进程）。

**根因**：`DaemonStatsReply` 自守护进程诞生起就没有任何调用点——
`DaemonHandleConn` 只解析 `Q ...`，收到 `STAT` 直接 return（无应答）。

**修复**：`DaemonHandleConn` 识别 `STAT` → `DaemonStatsReply(s)`。

## 二、拼音搜索（毫秒层新功能）

d/f 文件搜索支持三种匹配语义：**原名子串 / 全拼子串 / 首字母子序列**（首字母
要求 ≥2 字符防单字母噪声）。实测：`wxcszt` → `微信测试探针文档.txt`；
`weixin` → `微信支付交易明细.pdf` 与 `Weixin.exe` 同屏（原名与拼音双路并存）；
原名中文匹配不受影响。

### 设计要点

| 决策 | 取舍 |
| :--- | :--- |
| 只在守护进程启用 | `MemPinyinStart()` 检测 exe 同目录 `dict/` 后创建 Pinyin 实例；主程序自带一份实例不重复加载；dict 缺失时 `g_py` 保持空、功能静默降级为纯名字匹配 |
| 只转含汉字的名字 | 纯 ASCII 名字跳过（`pyOffs=0` 哨兵位），拼音池仅约 30% 条目占用，内存增量几 MB |
| 存全拼而非仅首字母 | 全拼可同时支持「全拼子串」与「首字母子序列」两种查询；仅存首字母无法答 `weixin` 这类全拼查询 |
| 缓存格式 v4 | 条目行后可选 `P\t<pinyin>` 行；版本头 `FTMEMINDEX4`，旧 v3 缓存自动弃用重建一次 |
| 转换时机 | 建库/增量重建（MemListRootFd→MemPoolAdd）时转换，3.9µs/条（见下），相对 fd 遍历的分钟级成本可忽略 |
| 并发 | `g_pyMu` 串行化建库线程与维护线程的并发转换（lib 线程安全性未声明） |

### 成本实测（build\pybench 微基准，8400 条混合中文文件名）

- 单条 API：3.9µs/条（33ms/8400）
- 批量 API：0.6µs/条（5ms/8400）——**没必要为 0.3s 的全库转换引入批量重构**

### 排查插曲：不要被「根构建 113 秒」带偏

首个根（桌面 8.4 万条）建库 113s，一度怀疑拼音转换是瓶颈；微基准证明转换
总计仅 ~0.3s，大头是 **fd 在 Defender 实时防护下的文件遍历本身**（约 1ms/文件）
加上当时另一个测试守护进程在同时跑 fd 抢 I/O。调优前先用微基准归因，
再动刀。

## 三、查询延迟的真相：恒定 500ms 是冷页回填

**现象**：守护进程重启后，连续多次查询恒定 ~500ms（连 0 命中的也 500ms），
与「暖态 20–40ms」的设计目标矛盾。

**归因**（`[disks] scan ms` 日志分解）：

| 状态 | 磁盘 blob 扫描（90MB） | 内存索引扫描（35 万条） |
| :--- | :--- | :--- |
| 冷启动首查 | 218–500ms | 0ms |
| 暖态稳态 | **31–47ms** | 0–5ms（拼音匹配后） |

冷态 = mmap 页缓存回填（一次性，守护进程常驻后不再发生）；暖态达标。
**结论：系统按设计工作，不需要进一步优化**——`[mems]`/`[disks]` 两条
`FT_DF_DEBUG` 日志由此常驻（分别打印扫描毫秒与命中数）。
（2026-10-25 第二轮：冷态成本已由预热线程挪到启动期、协议开销被批量化吃掉，
见本文第七节。）

## 四、缓存落盘锁外化

**问题**：`MemIndexSaveLocked` 在 `g_memMu`（搜索锁）内序列化 + 写 41MB 缓存，
每个根增量重建完成时，进行中的查询被卡 50–150ms。

**修复**：`MemIndexSave()`——锁内仅做快照（pool 是单个 wstring，拷贝 ≈ 一次
memcpy，~5ms），序列化 + 写盘 + 原子改名全部移到锁外；新增 `g_memSaveMu`
串行化建库线程与维护线程的并发保存（两者可能同时触发）。

## 五、其余修复/优化清单

| 项 | 说明 |
| :--- | :--- |
| 孤儿 fd 治理补全 | `FdCaptureLines`（内存/磁盘索引建库路径）此前未挂 KILL_ON_JOB_CLOSE Job——杀守护进程留下继续抢磁盘 I/O 的 fd 孤儿（实测抓到 3 个）。抽 `FdWalkerJob` 进程级单例，两条 spawn 路径统一挂载；实测杀守护进程 fd 子进程随之退出 |

| 守护进程每连接一线程 | 此前串行处理连接：STAT/诊断连接排队在长查询（全 blob 扫描秒级）后面，UI 线程的建库状态轮询被 2s 收包超时整个卡住。改 `_beginthreadex` 每连接短命线程（连接间无共享可变状态），线程创建失败退回串行 |
| 客户端协议加固 | 「N <count>」头解析失败整体按失败处理（调用方正确落 fd/WS 兜底；此前把垃圾当 0 命中且 ok=true，兜底被吞）；结果行必须是 `X:\` 绝对路径（防半行垃圾进结果） |
| `SearchDaemonStart` 限频 | 拉起限频 3s 一次 + 就绪等待 3s→1s 封顶：exe 在但起不来的病态场景（端口被占/安全软件拦杀）不再逐键卡 UI |
| 磁盘命中路径归一 | blob 存 fd 风格正斜杠 + 小写盘符：命中后统一转反斜杠、盘符大写（UI 拆 title/sub、跨层去重都依赖） |
| `wsquery` 增强 | `--bench` 支持 `--mem/--disk` 走守护进程层；`--memstat` 输出「建库全部完成」判定依赖的 STAT 现已真实可用 |
| 磁盘索引查询出锁 | `GetLongPathNameW`（文件系统调用，个别路径会挂死）移出 `g_diMu`：锁内只收集小写路径，出锁后还原大小写 |

## 六、冒烟验证方法（可复用）

1. **独立端口**：`FT_DF_DAEMON_PORT=48111` 起测试守护进程——注意单实例互斥体
   `Local\Flowtary.SearchDaemon` 全局唯一，**同时只能活一个守护进程**（与端口无关），
   换端口前先杀旧的。
2. **探针文件**：在桌面/文档各放一个唯一名字的探针（如 `zz_dfprobe_a2026.txt`），
   `wsquery --mem <探针词>` 应同时命中两处——这是「内存索引只扫首根」类 bug 的
   直接判据；中文名探针 + `wx…` 首字母查询验证拼音链路。
3. **Job 治理**：`taskkill /F` 杀守护进程后 `Get-Process fd` 应为空。
4. **协议级交叉验证**：`printf 'STAT\n' | … /dev/tcp/127.0.0.1/<port>` 手工对话，
   定位客户端 vs 服务端谁在说谎。
5. 建库观测：`FT_DF_DEBUG=1` 起守护进程，`[mem]`/`[mems]`/`[disks]`/`[conn]`/
   `[qcli]` 各阶段毫秒数落 stderr。

## 七、第二轮优化：协议批量化 + 冷页预热 + mem 饱和跳过磁盘（2026-10-25 下午）

> 对照第三节基线：暖态整链 78-250ms、冷首查 218-500ms、mem 名字扫描 31-47ms。
> 本轮后实测（生产守护进程 + `wsquery --bench 8 --mem weixin`）：
> **饱和查询（200 命中）恒定 15-16ms；0 命中最坏情况（四层全扫）62-110ms。**

### 1. 查询协议批量化（整链最大头）
- 服务端响应整包一次 `send`（原 200 命中 = 200+ 次小包）；STAT 应答同样合并。
- 客户端请求一次 `send`（头 + 词条 + 排除词）；两端读取改 4KB 缓冲 `LineReader`
  （原逐字节 recv，一查上万次系统调用，客户端/服务端各一遍）。
- 两端 `TCP_NODELAY`：环回上 Nagle+延迟 ACK 对小包可叠加百毫秒级 stall。
- 协议线上兼容：逐字节读端能解析整包发送端，新旧 exe 不需成对升级。

### 2. mem 饱和跳过磁盘扫描
`DaemonHandleConn`：mem 层已拿满 maxRows 时跳过磁盘层——合并阶段磁盘条目必然
全部丢弃，语义不变。常见词（如 `weixin`）省掉 90MB blob 扫描 + 一次路径兜底。

### 3. 磁盘索引冷页预热
守护进程启动映射就绪 / 重建完成换映射后，空闲优先级线程顺序读一遍索引文件
（缓存管理器与映射视图共享同一批物理页，读文件即暖页），把首查 218-500ms 的
页缓存回填挪到用户按键之前。`FT_DF_DEBUG` 下打 `[prefetch] ms`。

### 4. mem 扫描 ASCII 快路径
`MemCaselessFind` 逐字符 `towlower` CRT 调用占名字扫描大头（165K 条 31-47ms）。
改为：词条折叠在查询入口做一次（`MemFindFolded` 收已折叠词条），haystack 侧
ASCII 内联折叠、仅非 ASCII 走 `towlower`。名字扫描降到 0-16ms。
**教训**：第一版把折叠后 `wstring` 的构造留在 per-call 里，16 万次堆分配把
快路径收益吃光——热循环里连一次分配都不能有。

### 5. 两处 bug（冒烟抓出）
- **delta 路径双反斜杠**：`DiskWatchThread` 拼路径 `root`（"C:\"）+ `L"\\"` + rel
  → `"C:\Users\..."`，UI 打开/跨层去重都会踩。改为 root 已带尾分隔符就不重复加。
- **客户端 LineReader 作用域**：头部和结果行各建一个 reader——头部 reader 析构时
  缓冲里已收到的结果行全部丢失（服务端整包 send 后，剩余数据只在对端 FIN 才醒）
  → 恒「0 命中且 ok=true」。修复：整个响应用同一个 reader。
  （手工 socket 冒烟法再次立功：raw TCP 查询正常 → 一眼定位客户端在说谎。）

### 6. wsquery
- `PrintLine` 统一补换行（原先全部输出挤成一行，grep 只能整块捞）。
- `--bench` 与 `--mem/--disk` 组合此前不可达（单查分支先 return），调整分支顺序。

### 冒烟记录
- 探针文件（桌面+文档）、手工 TCP `Q/STAT`、`wxcszt` 拼音探针全通过；
- delta 新鲜度：守护进程生命周期内新建文件 2s 内可查，路径格式正确；
- 建库期间可查（缓存先行）：daemon 起后立即查询正常返回（略旧数据）。

## 八、第三轮：展示层排序质量 + 大小写还原缓存（2026-10-25 晚）

> 实测汇总（生产守护进程）：饱和查询 15-16ms（不变）、0 命中最坏 63ms、
> **800 行大查询暖态 47-62ms**（冷 860ms 仅守护进程重启后首查一次）。

### 1. UI 排序质量：截断不应发生在排序前
- 守护层请求 200 → **800 行**：UI 的质量排序（精确8/前缀4/包含2/路径1 + 点击
  权重）只能排它看得见的行。实测 `test` 查询：前 200 池序只有 **53** 个精确/
  前缀命中，800 行里有 **393** 个——旧截断把 86% 的高质量命中挡在排序器门外。
- `scoreOf` 补**拼音档**：词在名字与路径都不存在 = 守护进程拼音命中（文本过滤
  的 WS/fd 后端不可能产出这种行）→ 与名字包含同档计分。此前拼音结果得 0 分、
  压在仅路径命中（1 分）之下，正好把拼音用户最相关的结果埋掉。
- 删掉 UI 冗余的二次路径兜底查询：守护进程内部已按层做过 name→path 兜底并
  合并，UI 再查一遍纯浪费一轮往返。

### 2. PrefetchVirtualMemory 视图预取（替换读文件预热）
顺序读索引文件只暖缓存管理器的页，映射视图首触仍付软故障 + Defender 每进程
首访问开销（实测重启后首扫 172-609ms）。改为 `PrefetchVirtualMemory` 直接对
映射视图预取（KernelBase 运行时解析，Win8.1+；地址失效时优雅失败不崩），
旧系统回落读文件。

### 3. 目录级大小写还原缓存（本轮最大）
- **归因**：磁盘层每命中一次 `GetLongPathNameW` 在本机 Defender 下 6-8ms——
  `wx` 92 条中 34 条磁盘命中 = 250ms/查；UI 提到 800 行后最坏会到秒级。
- **方案**：按目录 `FindFirstFileW` 枚举一次得整目录「小写名→真名」映射，进程
  级缓存（`shared_ptr` 值保引用稳定）；查询发现缓存缺名（新建/改名）时自愈刷新
  一次，无需监听线程同步失效。暖态零文件系统调用。
- **实测**：冷 860ms（92 条命中跨 ~50 目录的一次性枚举）→ 暖 47-62ms。
- **教训（自摆乌龙）**：第一版把「当前组件」也拼进了父目录键——查找 "users"
  时搜的是 `c:\users` 自己的子目录表（自己找自己），恒 miss → 每查询触发全量
  refresh，比 GetLongPathNameW 还慢。冒烟日志 `[case] enum` 一眼定位。

### 4. 存量 bug：delta 键形不一致（自 c054769 起）
delta 表按真实大小写反斜杠存键，blob 命中过滤却用小写正斜杠路径查——**永远
匹配不上**：已删文件一直显示、重加文件重复显示。统一为小写反斜杠键
（`g_ovAdd` 的 value 保留真实大小写路径供展示）。

### 5. wsquery
`--rows N`：指定守护进程返回行数（验证 800 行窗口与延迟用）。

### 冒烟记录
- 大小写还原正确（`Desktop`/`Program Files` 真名）；delta 新建文件 47ms 命中
  且真名显示；饱和 15-16ms / 零命中 63ms / 拼音链路回归通过；
- 新旧 exe 混跑期间未发现协议异常（本轮协议未动）。

## 九、第四轮：内存索引 delta 即时新鲜度（2026-10-25 深夜）

> 问题：内存索引的增量粒度是「整根重扫」——桌面根 113s。用户目录树里新建的
> 中文文件要等整根重建才能拼音搜索（磁盘 delta 只兜底子串层，管不到拼音）。

### 方案：把磁盘层的成熟模式搬到内存层
- **监听线程**（原样只标脏）解析事件本体：增/改名 → `GetFileAttributesW` 判型 +
  `MemNameToPinyin` 即时转拼音 → `g_memDeltaAdd`；删/旧名 → `g_memDeltaDel`。
  属性解析不持锁（个别路径挂死只拖本监听线程，与磁盘监听同铁律）。
- **MemIndexSearch**：池命中过滤 `g_memDeltaDel`（窗口快照，竞态下轮收敛）；
  尾部合并 `g_memDeltaAdd`，匹配规则与池完全一致（名字 / 全拼子串 / 首字母子序列）。
- **整根重建换入时**按根前缀折叠清表（`MemDeltaDropRoot`，Build/Maint 两处调用）
  ——重建期间的新事件由监听继续入库、下轮收敛，与磁盘索引同一容忍窗口。
- delta > 5 万条放弃增量（洪峰交给整根重建）；delta 仅驻 RAM，重启靠缓存+全量重建。

### 实测
- 新建中文探针（微信维度测试文件.txt）**2s 内 `wxcs` 首字母拼音命中**；
- 删除后 2s 内从结果消失；ASCII 新文件 31ms 命中；
- 回归：饱和 15-31ms / 零命中 63ms / 800 行暖 47-62ms 均保持；
- 根重建换入折叠路径实测正常（`[memdelta] drop root=... add=N`）。

### 排查插曲：tasklist 会撒谎
tasklist 两次间歇性空输出，造成「守护进程已死」误判（甚至一度怀疑换入路径崩了，

## 十、第五轮：搜索索引档位设置（内存 ↔ 速度，用户可选）

> 设置「常规」页新增两档：「搜索索引档位」（4 档预设）+「拼音搜索」开关。
> 值存 `HKCU\Software\Flowtary\DfIndexTier`（默认 2）/ `DfPinyin`（默认 1）。

### 设计：守护进程自读注册表，主程序零传递
- **守护进程自己读注册表档位**（`DfTierFromReg`）：启动时应用条目上限
  （`ApplyTierCaps` 设 `FT_DF_MEMINDEX_MAX`/`FT_DF_DISKINDEX_MAX` 环境变量，
  建库前生效）与拼音开关；**任一查询连接或 60s 轮询发现变更即退出**
  （`DfTierChanged`，回 BYE 后 exit），主程序下轮查询自动按新档重拉
  （SearchDaemonStart 的 3s 拉起限频兜底）。wsquery 等旁路工具自动一致。
- **主程序门控**（tier 仅用于跳过守护层相关 UI/逻辑）：极简档不拉守护进程、
  不启动 STAT 轮询、不显示「索引建库中」提示，查询走 fd/WS 实时兜底。
- 缓存加载按档位上限裁根（`MemIndexLoadLocked` 逐根 `taken + size <= cap`），
  轻量档不被旧大缓存撑住；超限根落空等重建（重建同样受 cap 约束）。
- 磁盘索引 cap 只在建库时生效（现有 blob 不缩，反正是 standby 页）。

### 档位语义
| 档 | 内存索引 | 磁盘索引 | 守护进程 | 查询路径 |
|---|---|---|---|---|
| 极简 | 不建 | 不建 | 不驻留 | fd/WS 实时（秒级） |
| 轻量 | ≤10 万 | ≤200 万 | 驻留 | 毫秒级（覆盖小） |
| 均衡（默认） | ≤30 万 | ≤800 万 | 驻留 | 毫秒级（现状） |
| 极速 | ≤100 万 | ≤1600 万 | 驻留 | 毫秒级（大用户目录不截断） |

### 实测

- 拼音关：wxcs 全拼 0 命中、中文名直查正常；拼音开：根重建后 wxcs 恢复命中 ✓
- 运行中改 DfPinyin：下一连接自退出、重拉无缝（查询无失败感）✓

## 十一、第六轮：全盘拼音搜索（磁盘层拼音池）

> 此前拼音只在内存层（用户常用目录）；全盘中文文件名（D:\software\微信\… 等）
> 无法按拼音检索。本轮磁盘层补齐：**全盘任意中文文件名可按全拼搜**。

### 方案：blob 行尾拼音后缀（FTDISKIDX3）
- 建库：每行 = `D/F<小写路径>[|<basename 全拼>]`——仅汉字名附拼音
  （`MemNameToPinyin`，3.9µs/条 × 68 万 ≈ 3s，对 0.5-1.5h 建库可忽略），
  预计 blob 增量 ~3-4MB。
- 头部升 `FTDISKIDX3`：`COUNT` 行后新增 `PY\t0|1`（行尾是否含拼音后缀）。
  旧 v2 缓存头不符自动弃用重建一次。
- 扫描：按行内**首个 `|`** 切分路径段/拼音段（Windows 路径不含 `|`，非法字符）。
  名字模式命中 = 词在名字段 **或** 拼音段（全拼子串）；路径模式与排除词只看路径段
  （排除不得误伤拼音）。PY0 缓存 pyLen 恒 0，行为与 v2 完全一致。
- **首字母子序列不上磁盘层**：memchr 候选枚举只能发现连续子串，
  `wxcs ⊆ weixinceshi` 这类非连续命中候选扫描根本到不了那一行；要支持就得
  每行做子序列校验（扫描耗时翻倍）。首字母仍是内存层独有（实测踩过：
  wxcs 全拼命中而首字母 0 命中，据此修正设计）。
- 拼音开启但缓存是 PY0（关拼音期间建的）：启动映射后 `DiskMaybeStartRebuild`
  后台重建补上，旧映射照常服务不阻塞。

### 实测（FT_DF_DISKINDEX_ROOTS 小范围索引，4 条目秒级建库）
- `weixinceshi` → 微信测试探针.txt ✓；`zhifubao` → 支付 bao 账单.pdf ✓；
  `huiyijiyao` → 项目资料\会议纪要.docx ✓（均为磁盘层命中）
- 排除词边界：`weixinceshi -pytest` → 0（路径段排除生效）；
  `weixinceshi -ceshi` → 仍命中（拼音段不参与排除）✓
- blob 字节核对：`PY\t1` + `Dc:/…/项目资料|xiangmuziliao` ✓
- 全量建库后 90MB → 预计 ~93MB；扫描成本无变化（memchr 候选枚举不受行变长影响）

## 十二、第七轮：内存索引池 UTF-8 化（内存 −44%）+ 三处建库线程 bug

> 用户指令「继续优化，内存要小」。严格 A/B（同一份 158,957 条缓存、同环境、
> 同口径 t=10s）：**宽池 59.5MB → UTF-8 池 33.5MB 私有内存（−44%）**。

### 1. 内存索引池 UTF-8 字节化
- fd 建库输出与 memindex.dat 本就是 UTF-8——旧实现转 UTF-16 常驻再在落盘时转回，
  纯浪费。池/拼音池改 `std::string` 字节存储：路径主体是 ASCII（1 字节 vs 2 字节），
  16 万条省 ~40% 池内存；建库/加载/落盘全部零转换（还更快）。
- 查询热路径配套：`MemFindFoldedBytes`（ASCII 内联折叠、非 ASCII 仅在原始字节
  不等时解码→MemFoldChar→再编码——汉字等无大小写字符走零解码快路径；4 字节
  序列整体比对）；拼音池为小写 ASCII，全拼子串用 `strstr`、首字母子序列用
  `MemIsSubsequenceBytes`。命中条目才转宽（≤800 次/查）。
- delta 表维持宽字符（量小），与字节池在 MemIndexSearch 里两段合并。

### 2. 存量 bug：拼音缓存从未落盘成功（自 1cea4da）
`MemIndexSave` 的快照只拷 `pool/offs/nameFlags`，**漏了 `pyPool/pyOffs`**——
快照内拼音位恒空，P 行从未写入缓存。拼音一直只在单次守护进程会话内有效，
重启即丢、只能靠 delta/重建兜回来。两行修复（`grep -c "^P" memindex.dat`
从 0 → 2387 验证）。

### 3. 存量 bug：FdCaptureLines 预算在「有数据」分支失明
deadline 只在「fd 无输出」分支检查——两个 fd 并发爬行时 fd 持续低速吐数据，
预算形同虚设（实测 mem 走根 90 分钟不收敛）。语义修正：
- **FdCaptureLines 改「无输出超时」**（挂死保护）：持续输出不杀（磁盘全量建库
  合法地走 30-90 分钟，按总时长杀会得到永久残缺索引——本轮差点踩死），
  无输出超过 deadline（mem 120s / 磁盘 600s）才杀。
- **FdQuery（UI 流式）保持总预算**，但预算检查补进「有数据」分支。

### 4. 走根串行化 + 建库让路
- `g_fdWalkMu`：建库/维护/磁盘建库的 fd 遍历互斥——Defender 下并发 fd 互相拖慢
  （实测各慢 3-10 倍），串行化后每个走根独占 I/O。
- `g_memBuildDone`：初始全量建库期间维护线程让路（dirty 留在队列，建完统一收敛），
  消除初始建库期的重复走根。
- 内存 delta 洪峰上限 5 万 → 1 万条（百度网盘级 churn 场景 delta 内存上限 ~4MB；
  超限放弃增量交给整根重建，语义不变）。

### 实测
- 同条件 A/B：59.5 → 33.5MB（−44%）；tier1/关拼音档按比例再降。
- 功能回归：全拼（strstr 路径）5 命中、首字母（字节子序列）1 命中、中文名 14、
  800 行大查询 40 命中、暖查询 15-16ms——全部保持。
- 诊断基建：`[mem] T<tid> pass …` 线程归因日志（建库/维护并发走根可定位）、
  `[tier]` 启动档位日志。
- 环境注：百度网盘在 Documents 持续 churn（+6K tmp.node/会话）会拖慢 mem 走根
  并灌爆 delta——本轮多数「卡住」假象源于此 + 预算盲区，两者均已修。

## 十三、长期内存增长排查与修复（2026-10-27）

现场：守护进程私有内存 1648 MiB，工作集峰值 1554 MiB，系统记录
`RADAR_PRE_LEAK_64`。部署目录缺少 `fd.exe`，磁盘索引未就绪；旧状态工具把
“未就绪”统一显示成“建库中”。没有旧进程堆快照，不能把全部占用归因于单一对象。

- `FdCaptureStream` 替换整根 `vector<string>` 收集：内存索引逐行入池，磁盘索引
  逐行写 4 MiB 缓冲；管道改为 256 KiB、空管道轮询 10 ms，避免小管道叠加
  100 ms 等待把遍历吞吐拖垮。超长无换行输出有 1 MiB 上限。
- 磁盘 delta 同时限制 5 万条和估算 16 MiB；溢出释放节点与桶，使磁盘层失效并
  回落实时查询，后台重建恢复，缺失依赖/磁盘错误最多每分钟重试一次。
  重建按 generation 只折叠扫描开始前的事件，保留扫描期间的新变更。
- 重建失败、无输出超时、子进程异常退出和写盘失败都不会发布部分索引；
  替换前关闭旧文件映射，替换失败恢复旧缓存。
- `g_diBase` 单独保存映射基址，解除映射不再错误使用跳过 33 字节头的地址。
- 内存档位上限跨目录/文件两趟共享，维护线程按其余根已占条目计算剩余额度；
  零额度不会误传 `fd --max-results 0`（该参数代表无限制）。

- 大小写还原缓存增加估算 8 MiB 总额度，超大目录改为直接查路径大小写。
- 两个发布脚本补带独立的 `fd.exe`，并修正文档中“守护进程是 fd 改名”的旧描述。

  `Invalid UTF-16 surrogate pair`、守护进程退出。只对拼音键剔除非 BMP 字符和孤立
  代理项，原始路径完整保留；第三方转换异常回退原名匹配，不终止索引构建。

## 十四、第八轮：自研应用（workshop）秒出 + 应用 exe 全覆盖 + 路径显示（2026-10-29）

需求原话拆成四件事：workshop 里的 exe 要按版本号从大到小排、搜 workshop exe 要秒出、
chatgpt/software 这类应用 exe 搜得慢而且有时根本不出现、行尾路径显示不全。

### 根因

1. 内存池按「Desktop → 用户目录 → 注册表 IndexDirs」的顺序遍历，30 万条上限被
   桌面目录（本机 96 万条）先吃掉，`C:\workshop`、`C:\software` 拿到零额度；
   磁盘层和内存层都是「凑够 maxRows 就停」，截断发生在排序之前——几百万条里排在
   后面的应用 exe 被前面的噪声挤出候选窗。守护进程在内存层填满时直接跳过磁盘层。
2. workshop 的版本号目录（`aura-1.2.25`、`Flowtary-1.1.23.10`、`*-backup-20261028-1755`）
   以前只按文本命中分数排，快照备份和旧版本会压在最新版上面。
3. 行尾 sub 是父目录全路径，用 `DT_END_ELLIPSIS` 尾部截断——裁掉的正好是最深一层
   目录，也就是版本号所在的那一段。

### 改动

- 优先根（`IndexDirs`）插到池序最前，用户目录根排其后；内存层与磁盘层改为全量扫描
  + 按命中质量的排名堆（整名 8 / 前缀 4 / 名字或拼音包含 2 / 仅路径 1），预算
  `FT_DF_MEM_BUDGET_MS`（默认 60ms）只截「同分里的靠后根」，不再截掉优先根。
- 守护进程分两块回：首块 = 内存层 + 应用子索引（块尾 `MORE`），次块 = 磁盘层
  （块尾 `END`）；客户端按批上屏，首屏不再等几百毫秒的 blob 扫描。
- 应用子索引：从磁盘 blob 派生的 exe/lnk/appref-ms/msi 行偏移表（本机 18,689 条，
  约 73 KB），idle 优先级分块建表、blob 换版自动重建，守护进程启动即开始建。
  它补的是「池上限装不下的 Program Files / %LOCALAPPDATA%\Programs 里的应用」，
  首块只并入前 64 行（大小写还原按行付目录探测成本，超出部分交给磁盘层带真名送到）。
- `src/app_ver.h`：从路径里解析「应用名 + 点分版本号」（拒绝 `HWiNFO64`、`20261028`、
  `DirectX 9.0c` 这类假版本段），UI 排序先按文本分、再按「最新版 0 / 无版本信息 1 /
  旧版本 2」三档、再按版本降序；`*-backup-*`、`*-snapshot-*` 快照目录整条降级。
  断言在 `tools/appver_test.cpp`。
- 大小写还原从「整目录枚举 + 目录映射缓存」改成「逐组件精确名 FindFirstFile +
  组件小表缓存」。`tools/case_probe.exe` 现测：`C:\Windows\System32`（5007 项）整目录
  枚举 1505µs、精确名单查 75µs、`GetLongPathNameW` 276µs。旧缓存 12 MiB 上限装不下一趟
  800 行查询走过的上千个目录，超上限就整表清空、同批目录再枚举一遍——实测磁盘块
  大小写还原 516ms（blob 扫描本身 62ms）。新实现同一条查询：冷 63ms、暖 0ms，
  缓存上限也从 12 MiB 降到 4 MiB（每条 ~200B，不再自我淘汰）。
  探测失败（建库后文件已删）把小写原样入表，同一代 blob 内不重复探测；blob 换版清表。
- 行尾路径改 `DT_PATH_ELLIPSIS`（中段省略、保住最深一层目录），宽度按「标题显示后
  剩多少」给，上限 3/4、下限 1/4，另加 2px 余量避免刚好放得下却被省略。
  取证图：`build/path_ellipsis_160.png`、`build/path_ellipsis_260.png`
  （`tools/path_ellipsis_probe.exe`，同一批真实 workshop 路径、同字体同宽对比两种省略）。

### 实机 A/B（`wsquery --mem --rows 800`，多词按空格拆成独立参数）

### 已知边界（未在本轮处理）

- Microsoft Store（MSIX）应用不在文件系统枚举范围内：本机 ChatGPT 桌面版是
  `OpenAI.Codex_2p2nqsd0c76g0!App`，实体在 `C:\Program Files\WindowsApps`（普通进程
  列目录即 `Permission denied`），且开始菜单里没有对应 `.lnk`，所以 fd/内存/磁盘/应用
  子索引四层都看不见它。要搜到必须走 `shell:AppsFolder` 枚举 + AUMID 启动。
- 内存档位与 30 万条池上限没动：非优先根（Documents/Downloads/Program Files 等）
  仍可能被上限挤掉，应用子索引只补 exe/lnk 这一类。
  「索引目录」编辑器已在同日落到设置侧车（第 11 个 Tab，见 `SETTINGS_SIDECAR_FLTK.md` §8），
  但**上限本身没调**。
- 末段目录名本身长到放不下时，`DT_PATH_ELLIPSIS` 会硬裁右边缘（无省略号），
  例如 `C:\workshop\aura-1.2.25-backup-20261028-1755` 在 160px 下显示到 `-backup-2`。

### 验证与工具

- `appver_test`（版本解析断言）、`case_probe`（三种大小写还原通道耗时）、
  `path_ellipsis_probe`（省略号取证图）为新增目标。

  `C:\workshop`/`C:\software` 的行数——首块时间和优先根命中数一起看，才不会被
  「总命中数」骗到。
